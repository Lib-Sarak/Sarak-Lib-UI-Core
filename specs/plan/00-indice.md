# Índice de Implementação das Especificações

**É o arquivo de entrada obrigatório**: abra este arquivo sempre que for executar qualquer spec de `specs/plan/`, antes de editar qualquer coisa.

## Princípio vigente do planejamento

> ✅ **A Sarak-Lib-UI-Core é uma BASE de front com Shell + Design Engine central, consumida pelo modelo de MÓDULOS-PLUGIN** (decisão do mantenedor, executada pela [Spec 43](./43-design-system-primeiro.md), 2026-07-23). O sistema importador **registra seus módulos de negócio** (React) na base — `registerSarakModule`/`registerLocalComponent` — sobre `SarakUIProvider`+`SarakShell`; a base fornece o **Shell** (navegação/layout), o **Design Engine** (central de tema/template que aplica a TODA tela que consome os tokens `var(--sarak-*)`) e os **componentes atômicos** como blocos. O importador altera o layout pela central e pode **criar o que precisar** (módulo/componente próprio) — desde que use os tokens públicos para responder à central (marcação hardcoded fora do contrato de tokens NÃO é tematizada). É exatamente o padrão do `Sarak-MyService`, o único consumidor real da lib, agora oficial. O renderizador de páginas por manifesto (`src/core/Manifest/`) segue vivo e com suíte verde, mas **deixou de ser o modelo de consumo** — sai só na Spec 46, depois do Teste Real (Spec 40) provar o modelo de módulos-plugin em produção real.
>
> **(Histórico da virada, 2026-07-22 a 23)** O princípio anterior ("renderizador genérico, 100% via manifesto, zero React no consumidor") **falhou na prática**: o Teste Real bateu em 4 paredes numa tela simples; o motivo é estrutural (renderizador declarativo genérico é reconstruir uma linguagem em JSON — o gap nunca fecha). A lib sempre teve TRÊS arquiteturas em `src/core/` — #1 módulos-plugin (`Shell`+`Discovery`, Spec 04, o que o `Sarak-MyService` USA), #2 renderizador de páginas por manifesto (`Manifest`, o que FALHOU e ninguém usa), #3 componentes atômicos+Provider+Design Engine — e a decisão do mantenedor foi assumir o #1 como modelo oficial, com o Design Engine como central de layout e os componentes atômicos (#3) como blocos; remover só o #2 e o backend próprio.
>
> **(Histórico original)** **A Sarak-Lib-UI-Core é um renderizador genérico.** Ela declara CONTRATOS (tokens, gramática do manifesto, porta de persistência, fronteira de autenticação) e nunca escolhe a infraestrutura do consumidor (banco, provider, linguagem de backend, sistema de auth). Qualquer sistema que a importe deve montar 100% da sua interface via manifestos JSON — o piso de funcionalidade é o sistema `Sarak-MyService`. Origem deste princípio: dois testes reais de instalação plug-and-play (consumidores descartáveis `automacao` e `ERP`, 2026-07) + 2 relatórios de erro de agente, registrados em `00-progresso.md`.

### Fase 6 — Virada Design System (a tese manifesto-only falhou; pivô para design system React)

> Origem: o Teste Real (1ª versão da Spec 40) bateu em 4 paredes numa tela simples → "100% via manifesto" não sustenta produção. **Correção de premissa (2026-07-22):** a lib tem 3 arquiteturas — **#1 módulos-plugin** (`Shell`+`Discovery`, Spec 04, o que o `Sarak-MyService` USA), **#2 renderizador de páginas por manifesto** (`Manifest`, FALHOU/ninguém usa), **#3 componentes atômicos+Provider+Design Engine**. **Remove só o #2 e o backend próprio**; o **Design Engine é a central de layout que aplica ao sistema inteiro** e os componentes atômicos (#3) são os blocos. O módulo não está em produção — construir certo e remover o não-usado. O **Teste Real é o gate empírico** antes de remover o #2. Ordem: 43 → 44 → 45 → **40 (teste)** → 46 → 41 → 42.
>
> **Refino (auditoria do ERP real, 2026-07-24):** há **dois modos legítimos de consumo**, conforme a arquitetura do consumidor, e ambos partilham o mesmo núcleo (Provider + tokens + Design Engine central): **#1 Shell-host** — o `Sarak-MyService` usa (registra módulos no `SarakShell`); **#3 ui-kit + central** — o **ERP Earendel** usa (monorepo React puro, cada módulo é seu web app, Sarak entra como `packages/ui-kit` SEM `SarakShell` como host; removeu o Sarak por ADR 009 e o reintroduz como kit). A **Spec 40 reescrita testa o #3** (a forma real do ERP). O "modelo oficial único" da correção de 22/07 fica relativizado: não é #1 OU #3, é o **núcleo comum** servindo os dois.
