> **Contexto:** a rodada 2 (Spec 40.2) fechou cromo-em-todos-os-apps, ícones e responsividade **pontual** (só `SarakDataTable`→cards). A validação prática do dono apontou o gap central: **a adaptação de layout multidispositivo (celular/tablet/desktop) ainda não é abrangente** — o cromo não reflui no mobile (sidebar fixa de 240px come a tela; topbar só rola) e a maioria das telas/primitivas não consome as primitivas responsivas por padrão. **O menu hambúrguer é apenas UM exemplo concreto** do cromo não-adaptado, NÃO o pedido. O pedido é "layout multidispositivo por padrão". Esta é a **rodada 3 do ciclo 40.x** (Spec 40 §8).

# 1. Visão Geral e Objetivo

Tornar a **adaptação de layout por dispositivo abrangente e por padrão (zero-config)** — análogo ao que a L2 fez só para tabelas densas, estendido ao **cromo** e às **primitivas de layout/telas**. O consumidor **não escreve CSS nem media query**: o cromo e os componentes herdam as primitivas da Spec 16 (`useSarakDevice`, `ResponsiveValue<T>`, breakpoints) e se adaptam sozinhos. É **fix de lib** — o ERP não muda (herda via `ErpChrome`/componentes).

## 1.1 Princípios (carrega de 40.1/40.2)
- **Zero gambiarra; plug-and-play:** o consumidor não escreve CSS/media query para o layout adaptar — se precisar, é defeito da lib.
- **Renderizador GENÉRICO:** adapta-se em qualquer forma de deploy; o cromo é por-app (Spec 40.2 §1.2). A adaptação é do componente, não do host.
- **Zero-config com controle opcional:** os componentes têm **defaults mobile-first sensatos** E aceitam `ResponsiveValue<T>` para o consumidor refinar quando quiser. Nunca EXIGEM o consumidor passar valores responsivos para funcionar.

## 1.2 Escopo DELIMITADO (para não boilar o oceano)
**DENTRO:** (a) o cromo (`SarakAppChrome`); (b) as primitivas de layout (`SarakGrid`/`SarakFlex`/`SarakSplitPane` e os grids de Template que o ERP usa); (c) os componentes densos que o ERP usa (estende o tratamento da L2); (d) um **contrato de responsividade documentado** (o que adapta automaticamente). **FORA (registrar como follow-up, não fazer):** reescrever a responsividade de TODOS os componentes da lib numa rodada; qualquer componente que o ERP não usa fica registrado, não corrigido.

# 2. Estado atual (confirmado no código — não re-descobrir)
- **Cromo:** `SarakAppChrome` renderiza sidebar OU topbar por `design.navigationStyle`, **sem breakpoint** que reflua no mobile. Sidebar = largura fixa (`--sarak-sidebar-width`, 240px); topbar = `overflow-x-auto`. Não colapsa nem vira drawer no celular.
- **Densos:** `SarakDataTable`→cards no mobile já feito (40.2 L2). Vizinhos (`SarakTable`/`SarakManagementGrid`/`SarakDataGrid`) **sem** tratamento — follow-up registrado na 40.2.
- **Primitivas:** a lib TEM `useSarakDevice`, `SarakHidden`, `ResponsiveValue<T>`, breakpoints (Spec 16), mas o cromo e a maioria dos componentes **não os consomem por padrão**.

# 3. Regras de Negócio (Solução) — LADO DA LIB

## L1. Cromo responsivo por padrão (o item central)
- `SarakAppChrome` passa a **adaptar-se por dispositivo, zero-config**, via `useSarakDevice`/breakpoints (Spec 16):
  - **Desktop:** sidebar completa (atual) ou topbar, conforme `navigationStyle`.
  - **Tablet:** tier intermediário (ex.: sidebar colapsável/ícone-only, ou topbar compacta).
  - **Celular:** a nav **colapsa** — não ocupa a tela toda. **Padrão recomendado:** nav atrás de um **toggle** (drawer/hambúrguer) OU bottom-nav; conteúdo em coluna única full-width; paddings mais justos. *(O padrão concreto — drawer atrás de hambúrguer é o convencional — é DECISÃO DE DESIGN: o executor resolve deterministicamente pela árvore de decisão da lib; se genuinamente ambíguo, PARA e reporta (HITL). O importante é a nav ficar acessível e não comer a tela, não um widget específico.)*
- Acessível em todos os tiers (foco por teclado, `aria`, o toggle com `aria-expanded`/rótulo). Temável por token. Continua presentacional e por-app.

## L2. Primitivas de layout com defaults mobile-first + `ResponsiveValue`
- `SarakGrid`/`SarakFlex`/`SarakSplitPane` (e os grids de Template que o ERP usa): **default mobile-first sensato** (ex.: `SarakGrid` → 1 coluna no celular, reflui ao crescer; `SarakSplitPane` → empilha no celular; `SarakFlex` → wrap) E aceitam `ResponsiveValue<T>` para o consumidor controlar. Nenhum `grid-template-columns` fixo que estoure no mobile.
- Densidade/padding por dispositivo onde fizer sentido (via token responsivo), sem exigir CSS do consumidor.

## L3. Densos vizinhos que o ERP usa (estende a L2 da 40.2)
- Aplicar o mesmo tratamento mobile do `SarakDataTable` aos densos que o ERP **efetivamente usa** (checar: provavelmente `SarakTable`; talvez `SarakManagementGrid`). Os não-usados ficam registrados, não corrigidos.

## L4. Contrato de responsividade documentado
- Documentar (catálogo/skill) **o que adapta automaticamente** por dispositivo — para o consumidor saber o que herda de graça e onde pode refinar com `ResponsiveValue`. Fecha a expectativa "layout multidispositivo por padrão".

## Gates da lib (a cada fatia)
`catalog:check`; `barrel:check`; `npm run build` (DTS); **suíte COMPLETA** `npx vitest run` (incl. testes de breakpoint por dispositivo, simulando viewport); `package:check`; `run_audit.mjs` no **baseline**.

# 4. LADO DO ERP — herança (mínimo)
- O ERP **não escreve CSS de layout**. `Propostas/web` (e os demais) herdam a adaptação via `ErpChrome`/componentes. Ação normal de consumidor: no máximo, passar `ResponsiveValue` onde quiser um layout específico (opcional). Verificar que as telas ficam utilizáveis em celular/tablet/desktop sem CSS próprio.
