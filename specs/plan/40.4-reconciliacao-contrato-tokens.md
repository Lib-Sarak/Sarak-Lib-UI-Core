> **Contexto:** a validação de browser da Spec 40.3 (multidispositivo) expôs, no console, uma enxurrada de avisos `[Sarak:Design] Token "X" com valor fora do contrato — descartado.` para vários tokens da Design Engine (`searchPositionSidebar`=none, `cardVariant`=solid, `h1Weight`=800, `btnStyleType`=solid, `switchStyleType`=solid, `easeOut`=cubic-bezier(0,0,0.2,1), `surfaceMaterial`=solid, `systemTone`=neutral, `shadowColorMode`=monochrome). O sintoma é **ortogonal ao multidispositivo** (por isso NÃO foi enfiado na 40.3): é um **drift de contrato interno da própria lib** — o tema COMPLETO (montado a partir dos defaults/temas de referência pela 40.1 L6) carrega valores que o **validador estrito da Spec 44** recusa e descarta. É defeito de lib; o ERP só faz `spread` dos `SARAK_REFERENCE_THEMES` (nenhuma gambiarra no importador). Esta é a **rodada 4 do ciclo 40.x** (Spec 40 §8) — uma **correção**, não a fase de enablement (essa virou a Spec 50).

# 1. Visão Geral e Objetivo

Eliminar o drift entre **o que a lib emite** (valores de token nos defaults e nos temas de referência/globais que ela shippa) e **o que a lib aceita** (o contrato por token: enum `constraints.options` para `select`, faixa para `number`, tipo). Objetivo: **zero aviso `fora do contrato`** ao carregar os temas que a própria lib fornece, com o bloco de tokens hoje descartado (card/surface/shadow/tone/button/switch/easing/peso de título/posição de busca) **efetivamente aplicado** — sem afrouxar a validação (que é barreira de segurança da Spec 44). É **fix de lib**; o ERP herda (os warnings somem sem tocar no ERP).

## 1.1 Princípios
- **Reconciliar na FONTE, não afrouxar o guarda:** a solução é alinhar valor↔contrato token a token, **nunca** relaxar o `validateDesign` para "aceitar qualquer coisa" — isso reabriria o vetor que a Spec 44 fechou (tema é DADO, domínio de valores FECHADO).
- **Paridade 1:1:1:1:1:1 (Regra 4):** opção de token vive no schema (`constraints.options`); qualquer opção nova entra em sincronia com catálogo/gerados. Nada de opção órfã nem valor órfão.
- **Zero-gambiarra / plug-and-play:** defeito de lib corrige-se na lib; o consumidor não deve ver console poluído nem perder eixos de tema por importar os temas oficiais.
- **Preservar a intenção visual:** ao reconciliar, o tema de referência tem que **continuar com a mesma aparência pretendida** (caracterização por snapshot antes de mexer nos valores).

## 1.2 Escopo DELIMITADO (não boilar o oceano)
**DENTRO:** (a) auditar TODOS os tokens cujo `defaultValue`/`legacyValue` **ou** qualquer valor nos temas **shippados pela lib** (`SARAK_REFERENCE_THEMES`, `GLOBAL_THEMES`, presets) esteja fora do próprio contrato; (b) reconciliar cada um na fonte; (c) travar com um **gate** que impeça o drift de voltar. **FORA (registrar, não fazer):** redesenhar o sistema de tokens; adicionar tokens novos; mexer na responsividade (40.3), no bundle (41), no `SarakCoreCard` (42); afrouxar a semântica do validador.

# 2. Estado atual (confirmado no código — não re-descobrir)
- **O aviso** sai de [`src/core/Provider/utils/validation.ts:147`](../../src/core/Provider/utils/validation.ts) quando `coerceTokenValue` retorna `undefined`. Para `select`, isso ocorre quando o valor não está em `getEnumOptions(token)` (`validation.ts:114-120`); para `number/slider`, quando não é finito/clampável; para tipos string, quando não passa `isSafeCssString`.
- **Amostra confirmada:** `searchPositionSidebar` só declara `top|bottom|hidden` ([`schema/navigation.ts:295-299`](../../src/core/Design/schema/navigation.ts)), mas o tema completo manda `none` → descartado. O `sarak-sovereign` usa valores VÁLIDOS (`cardVariant:'classic'`, `surfaceMaterial:'frosted'`, `systemTone:'dark'`, `shadowColorMode:'neutral'`), logo os valores REJEITADOS (`solid`/`neutral`/`monochrome`/`800`/`none`/`cubic-bezier(...)`) vêm de **outra fonte no conjunto completo** — provável `minimalist-airy` e/ou os **defaults** que `buildThemeExportPayload`/`getDefaultDesignState` (40.1 L6) espalham para "resolver o tema COMPLETO". **O executor deve mapear a fonte exata de cada valor** (default do token vs. tema específico) antes de decidir o lado a corrigir.
- **Impacto:** os valores descartados caem no fallback → um conjunto de eixos de tema **não é aplicado** (contradiz o R10 "a config INTEIRA do Design Engine propaga"). Não é catastrófico (cor/fonte/cromo — os eixos-manchete — funcionam), mas é console poluído + config parcial + sinal de paridade quebrada.

# 3. Regras de Negócio (Solução) — LADO DA LIB

## L1. Auditoria completa do drift (a lista real, não só o console)
- Script/teste determinístico que percorre **cada token** do `MASTER_DESIGN_MAP` e cada valor emitido pelos temas **shippados pela lib** (defaults + `SARAK_REFERENCE_THEMES` + `GLOBAL_THEMES`/presets), e lista **todo** valor que `coerceTokenValue` rejeitaria (o console mostra só o que o boot tocou; a auditoria tem que ser exaustiva). Saída: por token, `{ fonte, valor, motivo (enum ausente / fora de faixa / tipo) }`.

## L2. Reconciliar cada drift NA FONTE (decisão token a token)
Para cada item da L1, decidir deterministicamente:
- **Valor é legítimo e o enum estava incompleto** → adicionar a opção ao `constraints.options` do token (com `id/value/label`), respeitando a paridade (catálogo/gerados sincronizados). Ex.: se `none` é um estado real de `searchPositionSidebar`, formaliza-se a opção — senão, troca-se o valor por `hidden`.
- **O conjunto de opções é canônico e o valor é que está errado** → corrigir o `defaultValue`/`legacyValue` do token OU o valor no tema de referência para uma opção válida, **preservando a aparência pretendida** (snapshot da L4 guarda contra regressão visual).
- **Regra dura:** não inventar opção só para calar o aviso; cada decisão tem que fazer sentido de design **e** de contrato. Sem afrouxar `validateDesign`.

## L3. Gate anti-regressão (o fix durável)
- Teste/gate na família de `catalog:check`/`barrel:check`: **falha o build** se qualquer `defaultValue`/`legacyValue` de token **ou** qualquer valor de um tema shippado pela lib cair fora do próprio contrato do token. Isso garante que um tema de referência novo (ou uma mudança de enum) nunca reintroduza o drift silenciosamente.

## L4. Caracterização + verificação de propagação
- **Antes** de mudar valores: snapshot de caracterização dos temas de referência afetados (aparência atual) para não regredir o visual pretendido.
- **Depois:** confirmar que os tokens antes descartados agora **aplicam** (viram `var(--sarak-*)` de verdade) e que o R10 passa a ser literal para esse bloco.

## Gates da lib (a cada fatia)
`catalog:check`; `barrel:check`; `npm run build` (DTS); **suíte COMPLETA** `npx vitest run`; `package:check`; `run_audit.mjs` no **baseline** (sem regressão). O gate novo da L3 entra no conjunto.

# 4. LADO DO ERP — herança (zero)
- Nenhuma mudança no ERP. Os `ERP_THEMES` fazem `spread` dos `SARAK_REFERENCE_THEMES`; uma vez limpa a fonte na lib e refrescado o `dist` (via `file:`), os avisos somem no console do ERP **sem uma linha tocada**. Verificar: abrir o ERP e confirmar console **sem** `fora do contrato`.

## 5.1 Achado colateral (fora de escopo, registrado)
O `PreviewCanvas` (Canvas do Design Engine, `src/features/DesignEngine/Canvas/`) renderiza o `design` de um tema diretamente, sem passar por `validateDesign` — por isso valores fora do contrato chegavam a virar CSS Variable literal ali (diferente do boot real via `useDesignManager`, que sempre valida antes de aplicar). O snapshot deste teste (`PreviewCanvas.test.tsx.snap`) capturava os valores INVÁLIDOS antigos e foi atualizado para refletir os valores corrigidos desta spec — a diferença do snapshot é só a prova de que os 21 tokens corrigidos agora aparecem com o valor certo nesse caminho de preview. Se o Canvas deveria validar como o boot real (hoje não valida) é uma decisão de escopo separada, não desta spec.
